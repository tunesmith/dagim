# dagim Design Spec

Status: working design draft  
Audience: implementation agent / Codex session  
Project name: `dagim`  
Primary command: `dagim FILE`

## 1. Summary

`dagim` is a terminal-first editor for small, single-file directed acyclic graphs.

The goal is to make graph-shaped thinking nearly as cheap as writing an outline, without forcing graph-shaped information into a tree. The core interaction is not visual graph drawing. The core interaction is fast textual entry, parent/child linking, graph navigation, durable completion state, and optional ordering of remaining work.

A graph edge:

```text
A -> B
```

means only:

```text
B cannot be processed before A.
```

The tool should avoid imposing stronger semantics. Depending on the domain, the same edge may mean prerequisite, parent/child, support, justification, enabling condition, dependency, or “must come before.” The graph model should preserve that flexibility.

## 2. Product Hypothesis

People often think in graphs, but commonly reach for trees because most writing and editing tools make trees cheap and graphs expensive. Outlines, folders, Markdown headings, and indentation all encourage tree-shaped representations.

`dagim` explores whether a small keyboard-first terminal tool can make DAG-shaped thought easy to capture, edit, navigate, and work through.

The tool should expose graph structure directly while remaining as lightweight as editing a text file.

## 3. Goals

Version 1 should support:

1. One graph per file.
2. Nodes with stable, visible, generated IDs and editable single-line text labels.
3. Node identity as the generated node ID, not the label text.
4. Directed edges from parent to child.
5. Strict DAG validation; cycles are not allowed.
6. Fast entry of new nodes.
7. Fast linking of parents and children.
8. Fast unlinking of parent/child edges without deleting nodes.
9. Node deletion.
10. Node text editing without changing identity.
11. Search and keyboard navigation across node text.
12. A readable, git-friendly plain-text file format.
13. Useful diffs for common changes.
14. A ready view showing incomplete nodes whose parents are complete.
15. Optional per-node completion state stored in the `.dagim` file.
16. A leaves view showing nodes with no children.
17. An ephemeral order mode for rehearsing an order for remaining incomplete work.

## 4. Non-goals for Version 1

Version 1 should not attempt to provide:

1. General cyclic graph support.
2. Multiple graphs per file.
3. Edge labels.
4. Multi-line node bodies.
5. Rich text.
6. Embedded images or attachments.
7. A canvas or visual node-link graph editor.
8. Automatic graph layout.
9. Graph database integration.
10. Cloud sync or collaboration.
11. Automatic generation of a canonical total topological order.
12. Semantic interpretation of edge meaning beyond “B cannot be processed before A.”
13. Completion timestamps, recurrence rules, or execution history.

## 5. Core Model

### 5.1 Node

A node has a stable, visible ID, an editable single-line text label, and optional completion state.

```text
NodeID = non-empty slug generated by dagim
NodeText = non-empty single-line string
Complete = boolean, default false
```

Node identity is the ID. The ID is stored in the file, shown when useful, and used by edges. It is not a hidden UUID.

The user should not have to invent IDs during ordinary use. When creating a node, the user enters only the node text. `dagim` generates a readable slug from that text and uniquifies it if needed.

Examples:

```text
People think in graphs -> people-think-in-graphs
Existing tools bias trees -> existing-tools-bias-trees
In gumbo pot, combine 1/2 cup butter and 1/2 cup white rice flour -> gumbo-pot-combine-butter-white-rice-flour
Prepare rice in rice cooker and press start -> prepare-rice-cooker-press-start
People think in graphs -> people-think-in-graphs-2
```

The node text remains the primary thing shown in the TUI. The ID exists to preserve stable identity across text edits and to keep diffs readable.

Renaming a node updates the text label but does not change the ID by default. A later explicit "rekey" command may be added if users want to change an ID intentionally.

Completion state marks whether a node has been done. Completion is current working state, not history: version 1 stores no timestamp and no event log. Completed nodes remain part of the graph and keep all parent/child edges.

The completed set must be dependency-closed:

1. A node can be marked complete only when all parents are complete.
2. Marking a completed node incomplete also marks every completed descendant incomplete.
3. Alternate upstream paths do not create an exception: if any required parent becomes incomplete, completed descendants are no longer valid.

Examples:

```text
people-think-in-graphs: People think in graphs
existing-tools-bias-trees: Existing tools bias trees
graph-reticence-ui-problem: Graph reticence is a UI problem
terminal-dag-editor-experiment: Terminal DAG editor experiment
```

### 5.2 Edge

An edge is a directed relation from parent to child:

```text
Parent -> Child
```

The only required interpretation is:

```text
Child cannot be processed before Parent.
```

UI labels may use terms such as parent/child, blocker/unblocked, upstream/downstream, or prerequisite/dependent, but the data model should not encode a specific semantic beyond ordering constraint.

### 5.3 DAG Invariant

The graph must always be acyclic.

An operation that would introduce a cycle must be rejected.

Examples of invalid edges:

```text
A -> A
A -> B when B already reaches A
```

### 5.4 File Order

The order nodes appear in the file is meaningful only as presentation order.

File order:

1. Is not graph order.
2. Is not a topological sort.
3. May be used to display search results, ready nodes, leaves, and parent/child lists in a stable human-controlled order.
4. Is persistently editable by the user.

The tool must not imply that file order creates additional graph constraints.

Version 1 should support moving visible rows earlier or later in file order from the TUI. In node view, `J/K` should reorder the highlighted parent or child within that displayed section; if no relationship row is selected, it should do nothing. In ready and leaves views, `J/K` should reorder the highlighted visible node within the current list section. Reordering nodes changes only presentation order and canonical serialization order. It must not add, remove, or imply edges.

## 6. Terminology

Preferred internal terms:

```text
node
edge
parent
child
frontier
available
blocked
ready
complete
order
```

Definitions:

```text
parent
  A node with an outgoing edge to the current node.

child
  A node with an incoming edge from the current node.

root
  A node with no parents in the actual graph.

frontier
  The set of nodes currently available to process in a graph state.

available / unblocked
  A node whose parents have all already been processed or temporarily removed.

ready
  An incomplete node whose parents are all complete.

blocked
  A node with at least one unprocessed parent.

complete
  Durable boolean node state stored in the `.dagim` file.

order
  A temporary user-created valid ordering of remaining incomplete nodes.
```

## 7. File Format

### 7.1 Recommended Extension

Use:

```text
.dagim
```

Example:

```text
ideas.dagim
```

### 7.2 Format Example

```text
# dagim v1

node people-think-in-graphs: People think in graphs

node existing-tools-bias-trees: Existing tools bias trees

node graph-reticence-ui-problem: Graph reticence is a UI problem
  complete
  parent people-think-in-graphs  # People think in graphs
  parent existing-tools-bias-trees  # Existing tools bias trees

node terminal-dag-editor-experiment: Terminal DAG editor experiment
  parent graph-reticence-ui-problem  # Graph reticence is a UI problem
```

### 7.3 Format Rules

The file format is line-oriented UTF-8 text.

Rules:

1. A file contains exactly one graph.
2. Blank lines are allowed and ignored semantically.
3. Comments begin with `#` and may appear anywhere a blank line may appear.
4. A node block begins with:

   ```text
   node <node-id>: <node text>
   ```

5. A parent reference appears inside a node block as:

   ```text
     parent <parent-node-id>  # <optional parent text hint>
   ```

6. Parent lines must be indented by two spaces in canonical output.
7. Completion state appears inside a node block as:

   ```text
     complete
   ```

8. Complete lines must be indented by two spaces in canonical output.
9. Node IDs are parsed as the token after `node` or `parent`.
10. Node text is parsed as the text after `node <node-id>:` with leading and trailing whitespace trimmed.
11. Internal whitespace, case, punctuation, and symbols in node text are preserved.
12. Empty node IDs are invalid.
13. Empty node text is invalid.
14. Newlines inside node text are invalid.
15. Duplicate node IDs are invalid.
16. Duplicate node text is allowed, though the UI may warn when exact duplicates are created.
17. Parent references must resolve to declared node IDs.
18. Parent references may refer to nodes declared later in the file.
19. Parent text hints after `#` are non-authoritative and ignored by the parser.
20. Self-edges are invalid.
21. Duplicate edges are invalid.
22. Cycles are invalid.

Node IDs should be readable ASCII slugs generated from the initial node text:

1. Lowercase where practical.
2. Tokenize words and numbers.
3. Drop low-information words for longer labels.
4. Drop common measurement quantities and units when they are likely to be incidental to identity.
5. Deduplicate repeated tokens.
6. Cap generated IDs to a compact readable length.
7. If no useful slug remains, use `node`.
8. If the slug already exists, append `-2`, `-3`, and so on.

The implementation may refine slugification for Unicode text, but the generated ID must be stable, readable, compact, and unique within the file.

### 7.4 Comments

For version 1, comments are allowed as standalone lines anywhere in the file:

```text
# This is a comment.
```

On parent lines, `#` begins an optional readability hint:

```text
parent graph-reticence-ui-problem  # Graph reticence is a UI problem
```

Canonical output may shorten long parent hints. Hints are for source readability only and do not affect parsing or graph identity.

A `#` inside node text is ordinary text:

```text
node review-rfc-42: Review RFC #42
```

The serializer may preserve comments if practical, but preserving comments is not required for the first implementation. If comment preservation is expensive, the first implementation may load comments and drop them on save, but this behavior should be documented in the UI or help text.

### 7.5 Canonical Serialization

When saving, the tool should write a canonical form:

```text
# dagim v1

node <node-id>: <node text>
  complete
  parent <parent-id>  # <parent text hint>
  parent <parent-id>  # <parent text hint>

node <node-id>: <node text>
```

Canonical serialization rules:

1. Emit the header comment `# dagim v1`.
2. Preserve node file order.
3. Emit each node exactly once.
4. Emit a `complete` line under completed nodes.
5. Emit parent references under the child node.
6. Sort parent references by file order, not alphabetically.
7. Emit current parent text hints in canonical parent lines.
8. Shorten long parent text hints to keep source and diffs readable.
9. Separate node blocks with one blank line.
10. End the file with a newline.

### 7.6 Why Parent References Only

The file stores parent references only, not child references.

Benefits:

1. Each edge is stored once.
2. Children are computed from parent references.
3. There is no redundant parent/child state to keep synchronized.
4. Adding a parent is a one-line diff.
5. Unlinking a parent is a one-line deletion.
6. Renaming a node is a small, stable diff because edge identity uses IDs.

### 8.1 Adding a Node

```diff
+# dagim v1
+
 node people-think-in-graphs: People think in graphs
+
+node existing-tools-bias-trees: Existing tools bias trees
```

### 8.2 Adding a Parent

```diff
 node graph-reticence-ui-problem: Graph reticence is a UI problem
   parent people-think-in-graphs  # People think in graphs
+  parent existing-tools-bias-trees  # Existing tools bias trees
```

### 8.3 Marking Complete

```diff
 node pull-fresh-transactions: Pull fresh transactions
+  complete
   parent open-banking-software  # Open banking software
```

### 8.4 Unlinking a Parent

```diff
 node graph-reticence-ui-problem: Graph reticence is a UI problem
   parent people-think-in-graphs  # People think in graphs
-  parent existing-tools-bias-trees  # Existing tools bias trees
```

### 8.5 Renaming a Node

Renaming a node changes its declaration text. References keep using the same ID. Canonical save may also refresh non-authoritative parent text hints.

```diff
-node existing-tools-bias-trees: Existing tools bias trees
+node existing-tools-bias-trees: Existing tools encourage tree thinking
 
 node graph-reticence-ui-problem: Graph reticence is a UI problem
   parent people-think-in-graphs  # People think in graphs
-  parent existing-tools-bias-trees  # Existing tools bias trees
+  parent existing-tools-bias-trees  # Existing tools encourage tree thinking
```

## 9. CLI Behavior

### 9.1 Primary Invocation

```text
dagim FILE
```

Behavior:

1. If `FILE` exists, load it.
2. If `FILE` does not exist, create a new empty graph associated with that path.
3. Open the interactive TUI.
4. Order remaining mode is entered from inside the TUI, not via a separate CLI command.

### 9.2 Other CLI Options

Useful basic options:

```text
dagim --help
dagim --version
dagim --check FILE       # parse and validate without opening TUI
```

Optional later options:

```text
dagim --print FILE       # print canonicalized file to stdout
dagim --export-dot FILE  # export Graphviz DOT
```

Do not implement optional later options unless the version 1 implementation is already solid.

`dagim --check FILE` should:

1. Parse the file.
2. Validate node IDs, parent references, duplicate edges, and cycles.
3. Print useful graph stats on success, such as node count, edge count, root count, and leaf count.
4. Report whether the file differs from canonical formatting, without modifying it.
5. Report transitive edges as warnings/suggestions.
6. Exit nonzero on parse, validation, or canonical-format errors if a strict/check mode is later added; v1 may exit zero for valid but noncanonical files if it clearly reports the formatting status.

Normal TUI autosave should preserve existing node IDs. Rekeying is an explicit migration/refactor operation because node IDs are stable identity.

## 10. TUI Overview

The TUI should optimize for keyboard-first editing and navigation.

The main experience is not a drawn graph. The main experience is moving through focused textual neighborhoods and graph frontiers.

Primary views:

1. Node view.
2. Search/jump view.
3. Ready view.
4. Leaves view.
5. Order remaining mode.
6. Help/command view.

When opening a non-empty graph, the TUI should start in the ready view. Empty files should start in the empty node state so the first action is still `a` to add a node.

The core capture loop should emphasize defining graph relationships while ideas are being created:

1. From the top-level or empty state, add a new node quickly.
2. From a selected node, add or link a parent quickly.
3. From a selected node, add or link a child quickly.
4. When adding a parent or child, select an existing node through search/autocomplete or create a new node from the prompt.
5. Support adding many unlinked beginning nodes first, but do not make "bulk capture now, link later" the only efficient workflow.

## 11. Node View

The node view is the focused editing view for a selected node.

Example:

```text
Parents
────────────────────────────────────────
  People think in graphs
  Existing tools bias trees

Current node
========================================
Graph reticence is a UI problem

Children
────────────────────────────────────────
  Terminal DAG editor experiment

Commands
────────────────────────────────────────
a add node    p add parent    c add child    x unlink selected
i inspect     e edit          d delete node  / search
r ready       l leaves        o order        C check
Space done/undone  v completed  R reset  W rewrite
J/K reorder   q quit          ? help
```

### 11.1 Node View Behavior

The user should be able to:

1. Focus parent nodes.
2. Focus child nodes.
3. Add a new node.
4. Edit the current node text.
5. Delete the current node.
6. Add/link an existing or new parent.
7. Add/link an existing or new child.
8. Unlink an existing parent or child.
9. Search all nodes by text.
10. Inspect a node to see details such as its ID.
11. Autosave successful edits immediately.
12. View ready nodes and leaves.
13. Mark nodes complete or incomplete.
14. Show or hide completed nodes.
15. Open a check/diagnostics view.

Normal node, ready, leaves, search, and order lists should show node text without inline IDs. Long node text should wrap to the terminal width. Node IDs should be available through inspect views, not through the main scanning surfaces.

Wrapped rows in selectable node lists should use a hanging indent on continuation lines so one long node does not visually read as multiple nodes.

On wide terminals, the TUI should remain left-anchored with a modest gutter and a capped content width. Separators and wrapped text should not stretch across an entire large monitor.

Command panels should render as aligned grids rather than hand-spaced prose rows. They should reflow to fewer columns on narrow terminals so command labels do not extend off-screen.

### 11.2 Suggested Keybindings

These are proposed defaults, not sacred API.

```text
j / Down      move selection down
k / Up        move selection up
Enter         focus selected node
Esc           go back / cancel current prompt
/             search nodes
a             add node
p             add/link parent to current node
c             add/link child to current node
x             unlink selected relationship
i             inspect selected node, or current node if no relationship is selected
e             edit current node text
d             delete current node, with confirmation if it has edges
r             show ready view
l             show leaves view
Space         mark selected/current node complete or incomplete
v             show/hide completed nodes
J / K         reorder selected visible row
o             order remaining incomplete nodes
C             show check/diagnostics view
R             reset all completion state, with confirmation
W             rewrite file: regenerate IDs, update references, save canonical format
?             help
q             quit, prompting only if autosave has failed and changes remain unsaved
ctrl+c        force quit immediately
ctrl+z        suspend to shell
```

## 12. Add and Link Behavior

### 12.1 Add Node

When adding a node:

1. Prompt for single-line node text.
2. Trim leading and trailing whitespace.
3. Reject empty text.
4. Generate a readable, unique node ID from the text.
5. Do not require the user to type or approve the ID during ordinary capture.
6. If the exact node text already exists, warn and offer to focus the existing node instead, but allow creating a separate node with a different generated ID.
7. Add the node to the persistent file order.

### 12.2 Add Parent

From current node `B`, adding parent `A` means adding:

```text
A -> B
```

Behavior:

1. Prompt with autocomplete over eligible existing node text.
2. If the selected text matches an existing node, use that node's ID.
3. If the text does not match an existing node, offer to create a new node and generate an ID for it.
4. Reject if the edge already exists.
5. Reject if it would create a cycle.
6. If the new parent is incomplete and the current node is complete, mark the current node and all completed descendants incomplete.
7. On success, keep focus on the current node unless user preference later says otherwise.

The autocomplete list should hide the current node, nodes already linked in the requested direction, and nodes that would create a cycle if linked. This is a usability filter; graph operations must still reject duplicate edges and cycles because typed exact matches can bypass the suggestion list.

Autocomplete lists should be height-aware. The prompt input and command hints must remain visible in normal terminal sizes; long match lists should render as a bounded window around the selected match and show the displayed range, for example `Matches 8-13 of 25`.

### 12.3 Add Child

From current node `A`, adding child `B` means adding:

```text
A -> B
```

Behavior mirrors Add Parent.

### 12.4 Unlink

Unlinking removes an edge but does not delete either node.

From current node:

1. If a parent is selected, remove `parent -> current`.
2. If a child is selected, remove `current -> child`.
3. Confirm only if the UI makes accidental unlinking likely.

## 13. Edit Node Text Behavior

Because node identity is the stable ID, editing a node changes only the node's text label by default.

Edit:

```text
old text -> new text
```

Rules:

1. Reject empty new text.
2. Allow duplicate text because the node ID is identity.
3. Update the node declaration text.
4. Preserve the node ID.
5. Preserve all incoming and outgoing edges.
6. Preserve file order position.
7. Canonical save may refresh parent text hints that mention the old text.

## 14. Delete Behavior

Deleting a node removes the node and all incident edges.

Rules:

1. If the node has no parents and no children, delete immediately or with light confirmation.
2. If the node has parents or children, require confirmation.
3. Do not delete neighboring nodes.
4. After deletion, focus a nearby node if possible.
5. If graph becomes empty, show an empty-graph state.

Example:

```text
A -> B -> C
```

Deleting `B` removes `B`, `A -> B`, and `B -> C`.

It does not create `A -> C` automatically.

## 15. Search and Autocomplete

Search is central because node text is the primary human-facing label.

Version 1 search should support:

1. Case-insensitive substring matching.
2. Display matches in file order.
3. Keyboard selection.
4. Enter to focus.
5. Height-bounded result windows so the search header, input, and footer remain visible on short terminals.

Autocomplete prompts for parent/child linking should reuse the same search behavior.

Optional later improvement:

1. Fuzzy matching.
2. Recent nodes.
3. Ranked matches.
4. Alias support.

Do not add aliases in version 1.

## 16. Ready View

The ready view shows incomplete nodes whose parents are all complete.

Example:

```text
Ready
────────────────────────────────────────
  People think in graphs
  Existing tools bias trees
```

This is the default working frontier for checklist-style use. With no completed nodes, ready usually matches the graph roots. As nodes are marked complete, their incomplete children become ready.

Rules:

1. Display ready nodes in file order.
2. Open here by default for non-empty graphs.
3. Do not automatically linearize the graph.
4. Enter focuses a selected node.
5. Space toggles the selected ready node complete or incomplete. Marking a completed node incomplete cascades to completed descendants.
6. `a` adds a new unlinked node; because it has no parents and is incomplete, it appears in ready until completed or linked behind an incomplete parent.
7. `o` enters order remaining mode.
8. `v` toggles visibility of completed nodes for review.
9. `R` asks for confirmation and clears all completion state.
10. Search/filter may be available.
11. Inspect should expose IDs without showing IDs inline in the ready list.
12. `J/K` reorders the highlighted ready row within the ready section. When completed nodes are visible, `J/K` also reorders highlighted completed rows within the completed section.

Ready is a property of current completion state plus graph structure. True roots are still graph-theoretic nodes with no parents, but roots are not the primary workflow view in version 1.

## 16.5 Leaves View

The leaves view shows all nodes in the actual graph that currently have no children.

Example:

```text
Leaves
────────────────────────────────────────
  Terminal DAG editor experiment
  Publish first release
```

This view is useful because leaves often indicate graph endpoints: places where a brainstorming graph may be complete, or places where more child nodes may need to be added.

Rules:

1. Display leaves in file order.
2. Do not automatically linearize the graph.
3. Enter focuses a selected node.
4. `r` switches to ready view.
5. Search/filter may be available.
6. Inspect should expose IDs without showing IDs inline in the leaves list.
7. `J/K` reorders the highlighted visible leaf.
8. Esc returns to the view that opened leaves.

Leaves are a property of the graph. A node is a leaf only because it currently has no children; it is not a distinct node type.

## 17. Order Remaining Mode

Order remaining mode is an ephemeral planning tool.

It is based on the same idea as Kahn’s algorithm for topological sorting, but it starts from durable completion state and only orders remaining incomplete nodes. Instead of choosing tied/unblocked nodes automatically, the tool asks the user to choose each next node.

The tool should not present this as “the” topological sort. It is a scratch user-authored valid ordering for unfinished work.

### 17.1 Mode Entry

Order remaining mode is entered from inside the TUI with:

```text
o
```

It should be available from both node view and ready view.

There should not be a required separate CLI command for version 1.

### 17.2 Conceptual Model

Ordering maintains temporary state:

```text
base: set of nodes already complete in the graph
processed: base plus nodes chosen in this ordering session
output: ordered list of chosen incomplete nodes
available: incomplete nodes whose parents are all in processed
```

The underlying graph is not mutated by ordering.

Version 1 should not persist order mode state inside the `.dagim` file. Completion state is persistent; order state is temporary exploratory state. Users may export a linearized list, undo, reset the temporary ordering, or exit the mode without changing the graph.

At each step:

1. Compute all currently available unprocessed incomplete nodes.
2. Present them to the user.
3. User chooses one.
4. Add it to the output list.
5. Mark it temporarily processed.
6. Recompute available nodes.
7. Repeat until all nodes are processed or the user exits.

### 17.3 Display

Default display should emphasize:

1. The order produced so far.
2. The currently available nodes.

Example:

```text
Order remaining
────────────────────────────────────────
1. People think in graphs
2. Existing tools bias trees

Available now
────────────────────────────────────────
  Graph reticence is a UI problem

Commands
────────────────────────────────────────
Space pick    Enter inspect    u undo    r reset
e export      Esc/q exit
```

The mode does not need to display “still blocked” by default. That can make the interface heavier and more like an analysis dashboard. Users should be able to inspect available nodes and temporarily drill into their parent/child neighborhoods if needed.

Optional later enhancement:

```text
show blocked count
show blocked nodes
show why selected blocked node is unavailable
```

### 17.4 Available Node Ordering

Available nodes are displayed in file order by default.

This display order is non-semantic. It does not mean the graph says one available node comes before another.

### 17.5 Inspecting During Order

In order remaining mode:

```text
Enter
```

on an available node should inspect or focus that node without picking it.

A lightweight inspect view should show:

```text
Node text
Parents
Children
```

Returning from inspect mode should return to the same order state.

### 17.6 Picking

Picking an available node adds it to the output order and temporarily treats it as processed.

Suggested key:

```text
Space
```

### 17.7 Undo

Ordering is exploratory, so undo should be part of version 1.

Rules:

1. Undo removes the most recently picked node from output.
2. The node becomes unprocessed again.
3. Available nodes are recomputed.
4. Multiple undo operations are allowed.

### 17.8 Reset

Reset clears the temporary order state.

The graph itself is not changed.

### 17.9 Completion

When all remaining incomplete nodes have been picked, show the completed order.

Example:

```text
Order complete
────────────────────────────────────────
1. People think in graphs
2. Existing tools bias trees
3. Graph reticence is a UI problem
4. Terminal DAG editor experiment

Commands
────────────────────────────────────────
e export    u undo    r reset    Esc/q exit
```

### 17.10 Exporting the Order

Version 1 should support a simple export of the current order.

Possible behavior:

1. Prompt for output path.
2. Default to:

   ```text
   <input-file>.order.txt
   ```

3. Write one node per line, in chosen order.

Example output:

```text
People think in graphs
Existing tools bias trees
Graph reticence is a UI problem
Terminal DAG editor experiment
```

The exported order is not the graph file and should not mutate the graph.

## 18. Cycle Detection

Any operation that adds an edge must check for cycles.

To add:

```text
A -> B
```

## 18.5 Transitive Edge Warnings

A direct edge is transitive when the child is still reachable from the parent through another path after ignoring that direct edge.

Example:

```text
A -> D
A -> B -> C -> D
```

In this case, `A -> D` is redundant under dagim's minimal edge meaning because `A` already must come before `D` through `B` and `C`.

Version 1 should report transitive edges from `dagim --check FILE` and the TUI check view. It should not remove them automatically during rewrite. Removing transitive edges is a graph-changing simplification, not formatting.

Reject if:

```text
A == B
```

or if there is already a path:

```text
B -> ... -> A
```

Error messages should be explanatory and, if practical, show the cycle path.

Example:

```text
Cannot add edge:
  Terminal DAG editor experiment -> People think in graphs

That would create a cycle:
  People think in graphs
  -> Graph reticence is a UI problem
  -> Terminal DAG editor experiment
  -> People think in graphs
```

Raw files loaded from disk must also be validated for cycles. If a file contains a cycle, the tool should refuse normal editing and show a clear validation error with enough information to repair the file manually.

## 19. Graph Algorithms

### 19.1 Children Computation

Children are computed from parent references.

For each node ID `B` with parent ID `A`:

```text
parents[B].add(A)
children[A].add(B)
```

### 19.2 Ready

Ready nodes are incomplete nodes whose parents are all complete.

```text
ready = nodes where complete[node] is false
        and every parent in parents[node] has complete[parent] true
```

Display ready nodes in file order.

### 19.3 Leaves

A leaf is any node with zero children.

```text
leaves = nodes where children[node] is empty
```

Display leaves in file order.

### 19.4 Order Remaining

Order remaining mode is a user-directed topological traversal over incomplete nodes.

Pseudocode:

```text
processed = set of completed nodes
output = empty list

while len(processed) < len(nodes):
    available = []

    for node in file_order:
        if node not in processed and every parent of node is in processed:
            available.append(node)

    if available is empty:
        error: graph is cyclic or invalid

    chosen = user picks one node from available
    processed.add(chosen)
    output.append(chosen)
```

Because the graph is validated as acyclic before entering this mode, `available` should never be empty unless all nodes are processed.

### 19.5 Path Search

Path search is needed for cycle detection and useful error reporting.

To test whether adding `A -> B` creates a cycle, search for an existing path from `B` to `A`.

If found, the cycle is:

```text
A -> B -> ... -> A
```

## 20. Suggested Internal Architecture

The implementation should keep graph logic independent from TUI logic.

Suggested modules/packages:

```text
graph
  core data structures
  add/delete/edit/link/unlink operations
  validation
  cycle detection
  ready, roots, leaves, and file-order operations
  completion and temporary order state

format
  parse .dagim files
  serialize canonical .dagim files
  line-numbered parse errors

ui
  TUI state machine
  views
  keybindings
  prompts
  search/autocomplete

cmd
  CLI entrypoint
```

This separation is important. Most correctness should be testable without a terminal UI.

## 21. Suggested Implementation Stack

A good default implementation stack would be:

```text
Go + Bubble Tea
```

Reasons:

1. Easy single-binary distribution.
2. Fast startup.
3. Good fit for terminal applications.
4. Reasonable state/update/view architecture.
5. Keeps the project practical rather than turning it into a language experiment.

This is a suggestion, not a product requirement. The spec is intentionally language-agnostic except where it describes CLI and file behavior.

## 22. State and Persistence

### 22.1 Autosave

The TUI should autosave after every successful graph mutation.

Autosaved changes include:

1. Node added.
2. Node text edited.
3. Node deleted.
4. Edge added.
5. Edge removed.
6. Completion state changed.
7. File order changed.

Autosave behavior:

1. Validate the graph.
2. Serialize canonical text.
3. Write atomically where practical:
   - write temp file in same directory
   - flush/close
   - rename over original
4. Clear dirty state on success.
5. If autosave fails, keep the in-memory change, mark the graph dirty, and show an error.

There is no normal manual save key in v1. `W` remains the explicit rewrite/rekey command.

### 22.3 Quit

If quitting with `q` and autosave has failed, prompt:

```text
Autosave failed. Retry save before quitting? [y]es / [n]o / [c]ancel
```

`ctrl+c` should always force quit from any mode without prompting. `ctrl+z` should suspend to the shell from any mode, matching normal terminal expectations for a raw-mode TUI.

## 23. Error Handling

The tool should provide clear errors for:

1. Empty node text.
2. Empty node ID.
3. Duplicate node ID.
4. Unknown parent reference in file.
5. Self-edge.
6. Duplicate edge.
7. Cycle creation.
8. Invalid file syntax.
9. Delete confirmation for connected node.
10. Save failure.
11. Export failure.

Errors should be specific and actionable.

Bad:

```text
Invalid graph.
```

Good:

```text
Unknown parent on line 14:
  existing-tools-bias-trees

No node with that ID is declared.
```

## 24. Empty Graph Behavior

When opening a new or empty file, show an empty state:

```text
No nodes yet.

Commands
────────────────────────────────────────
a add first node    ? help    q quit
```

## 25. MVP Acceptance Criteria

A version 1 implementation is acceptable when all of the following work:

### 25.1 File Loading

Given:

```text
# dagim v1

node a: A

node b: B
  parent a  # A
```

`dagim file.dagim` loads the graph with nodes `a`, `b` and edge `a -> b`.

### 25.2 File Saving

Saving writes canonical `.dagim` text with one node block per node and parent ID references under child nodes.

### 25.3 Add Node

The user can add a new single-line node from the TUI.

### 25.4 Generate Stable ID

Adding a node generates a readable unique ID from the node text without asking the user to type the ID.

### 25.5 Duplicate Text Warning

Adding a node with text equal to an existing node warns or redirects to focusing the existing node, while still allowing a separate node if the user confirms.

### 25.6 Add Parent

From node `B`, adding parent `A` creates edge `A -> B`.

### 25.7 Add Child

From node `A`, adding child `B` creates edge `A -> B`.

### 25.8 Unlink

The user can remove `A -> B` without deleting `A` or `B`.

### 25.9 Edit Node Text

Editing node ID `a` from text `A` to text `A2` preserves node ID `a`, preserves all edges, and updates canonical parent text hints on autosave.

### 25.10 Delete

Deleting a node removes that node and all incident edges, but no neighboring nodes.

### 25.11 Cycle Rejection

Given existing graph:

```text
A -> B -> C
```

attempting to add:

```text
C -> A
```

is rejected with a clear message.

### 25.12 Ready And Leaves Views

The user starts on ready for a non-empty graph, can view incomplete nodes whose parents are complete, can add a new node, can mark a selected ready node complete, and can enter order remaining mode.

The user can open leaves and view all nodes with no children, then focus a selected leaf.

### 25.13 Search

The user can search node text and focus a selected result.

### 25.14 Reorder File Order

The user can move a selected parent or child row earlier or later within its displayed section without changing graph edges. This is implemented by changing persistent file order.

### 25.15 Check Command

`dagim --check FILE` validates the file without opening the TUI and prints useful graph stats, including ready, complete, roots, and leaves counts, on success. It also reports transitive edge warnings.

The TUI check view should also indicate whether `W` rewrite would change node IDs and list the prospective ID changes. A valid graph may still have rewrite ID changes pending because validity is about graph invariants, not whether current stable IDs match generated slugs from current text. Transitive edge diagnostics should stay compact and wrap to the terminal width rather than dumping long paths across the screen. If the diagnostics exceed the terminal height, Check should provide in-app scrolling and keep its footer visible.

### 25.16 Rewrite Command

From inside the TUI, `W` asks for confirmation, regenerates node IDs from current node text, updates parent references, writes current canonical format, and saves the file.

### 25.17 Completion State

Marking a node complete adds `complete` to that node block. Marking it incomplete removes that line. Reset completion removes all `complete` lines.

### 25.18 Order Remaining Mode

Given graph:

```text
A -> C
B -> C
```

order remaining mode initially shows `A` and `B` as available when neither is complete.

If the user picks `A`, then `B` remains available and `C` remains unavailable.

If the user then picks `B`, `C` becomes available.

If `A` is already complete before entering order mode, the mode starts with `B` available and does not include `A` in output.

### 25.19 Order Undo

The user can undo the most recent pick and the available set is recomputed correctly.

### 25.20 Order Export

The user can export the current or completed order as one node per line.

## 28. Open Decisions

These can be decided during implementation:

1. Should comments be preserved exactly on save, or can v1 canonicalization drop them?
2. Should the UI primarily say “parents/children” or “blockers/unblocked by”?
3. Should order export be available before the order is complete?
4. Should deleting a connected node require typing the node text, or is a simple confirmation enough?
5. Should search be substring-only in v1, or fuzzy from the beginning?
6. How aggressively should slug generation normalize Unicode text?

Recommended v1 defaults:

1. Comment preservation is nice but not required.
2. Use “parents/children” in node-editing views.
3. Use “ready” for durable completion workflow and “available” inside order mode.
4. Allow export of partial and complete orders.
5. Start with substring search.
6. Implement simple readable ASCII slug generation and uniquification.

## 29. Implementation Prompt for Codex

Build `dagim`, a terminal-first editor for small single-file DAGs, using this document as the source of truth.

Start with correctness before UI polish:

1. Implement the graph model and pure operations.
2. Implement parser and serializer for `.dagim` files.
3. Add unit tests for parser, serializer, graph operations, validation, reordering, slug generation, completion state, and order state.
4. Implement CLI entrypoints `dagim FILE` and `dagim --check FILE`.
5. Implement the TUI with node view, search, ready view, leaves view, completion toggling, file-order reordering, whole-file rewrite/rekey, and order remaining mode.
6. Ensure cycle rejection and edit behavior are correct.
7. Ensure saving writes stable canonical diffs with visible node IDs and refreshed parent text hints.

The most important product behavior is that the tool never silently collapses the DAG into an arbitrary total order. In order remaining mode, the user chooses among currently available nodes.

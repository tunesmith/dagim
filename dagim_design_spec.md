# dagim Design Spec

Status: working design draft  
Audience: implementation agent / Codex session  
Project name: `dagim`  
Primary command: `dagim FILE`

## 1. Summary

`dagim` is a terminal-first editor for small, single-file directed acyclic graphs.

The goal is to make graph-shaped thinking nearly as cheap as writing an outline, without forcing graph-shaped information into a tree. The core interaction is not visual graph drawing. The core interaction is fast textual entry, parent/child linking, graph navigation, and manual sequencing through currently unblocked nodes.

A graph edge:

```text
A -> B
```

means only:

```text
B cannot be processed before A.
```

The tool should avoid imposing stronger semantics. Depending on the domain, the same edge may mean prerequisite, parent/child, support, justification, enabling condition, dependency, or “must come before.” The graph model should preserve that flexibility.

## 2. Product Hypothesis

People often think in graphs, but commonly reach for trees because most writing and editing tools make trees cheap and graphs expensive. Outlines, folders, Markdown headings, and indentation all encourage tree-shaped representations.

`dagim` explores whether a small keyboard-first terminal tool can make DAG-shaped thought easy to capture, edit, navigate, and manually process.

The tool should expose graph structure directly while remaining as lightweight as editing a text file.

## 3. Goals

Version 1 should support:

1. One graph per file.
2. Nodes with stable, visible, generated IDs and editable single-line text labels.
3. Node identity as the generated node ID, not the label text.
4. Directed edges from parent to child.
5. Strict DAG validation; cycles are not allowed.
6. Fast entry of new nodes.
7. Fast linking of parents and children.
8. Fast unlinking of parent/child edges without deleting nodes.
9. Node deletion.
10. Node rename/refactor.
11. Search and keyboard navigation across node text.
12. A readable, git-friendly plain-text file format.
13. Useful diffs for common changes.
14. A roots view showing nodes with no parents.
15. A manual sequencing mode based on “show currently unblocked nodes, user picks one, repeat.”

## 4. Non-goals for Version 1

Version 1 should not attempt to provide:

1. General cyclic graph support.
2. Multiple graphs per file.
3. Edge labels.
4. Multi-line node bodies.
5. Rich text.
6. Embedded images or attachments.
7. A canvas or visual node-link graph editor.
8. Automatic graph layout.
9. Graph database integration.
10. Cloud sync or collaboration.
11. Automatic generation of a canonical total topological order.
12. Semantic interpretation of edge meaning beyond “B cannot be processed before A.”

## 5. Core Model

### 5.1 Node

A node has a stable, visible ID and an editable single-line text label.

```text
NodeID = non-empty slug generated by dagim
NodeText = non-empty single-line string
```

Node identity is the ID. The ID is stored in the file, shown when useful, and used by edges. It is not a hidden UUID.

The user should not have to invent IDs during ordinary use. When creating a node, the user enters only the node text. `dagim` generates a readable slug from that text and uniquifies it if needed.

Examples:

```text
People think in graphs -> people-think-in-graphs
Existing tools bias trees -> existing-tools-bias-trees
In gumbo pot, combine 1/2 cup butter and 1/2 cup white rice flour -> gumbo-pot-combine-butter-white-rice-flour
Prepare rice in rice cooker and press start -> prepare-rice-cooker-press-start
People think in graphs -> people-think-in-graphs-2
```

The node text remains the primary thing shown in the TUI. The ID exists to preserve stable identity across text edits and to keep diffs readable.

Renaming a node updates the text label but does not change the ID by default. A later explicit "rekey" command may be added if users want to change an ID intentionally.

Examples:

```text
people-think-in-graphs: People think in graphs
existing-tools-bias-trees: Existing tools bias trees
graph-reticence-ui-problem: Graph reticence is a UI problem
terminal-dag-editor-experiment: Terminal DAG editor experiment
```

### 5.2 Edge

An edge is a directed relation from parent to child:

```text
Parent -> Child
```

The only required interpretation is:

```text
Child cannot be processed before Parent.
```

UI labels may use terms such as parent/child, blocker/unblocked, upstream/downstream, or prerequisite/dependent, but the data model should not encode a specific semantic beyond ordering constraint.

### 5.3 DAG Invariant

The graph must always be acyclic.

An operation that would introduce a cycle must be rejected.

Examples of invalid edges:

```text
A -> A
A -> B when B already reaches A
```

### 5.4 File Order

The order nodes appear in the file is meaningful only as presentation order.

File order:

1. Is not graph order.
2. Is not a topological sort.
3. May be used to display search results, available nodes, roots, and parent/child lists in a stable human-controlled order.
4. Is persistently editable by the user.

The tool must not imply that file order creates additional graph constraints.

Version 1 should support moving nodes earlier or later in file order from the TUI. Reordering nodes changes only presentation order and canonical serialization order. It must not add, remove, or imply edges.

## 6. Terminology

Preferred internal terms:

```text
node
edge
parent
child
frontier
available
blocked
manual sequence
```

Definitions:

```text
parent
  A node with an outgoing edge to the current node.

child
  A node with an incoming edge from the current node.

root
  A node with no parents in the actual graph.

frontier
  The set of nodes currently available to process in a graph state.

available / unblocked
  A node whose parents have all already been processed or temporarily removed.

blocked
  A node with at least one unprocessed parent.

manual sequence
  A user-created valid topological ordering produced by repeatedly picking from the current frontier.
```

## 7. File Format

### 7.1 Recommended Extension

Use:

```text
.dagim
```

Example:

```text
ideas.dagim
```

### 7.2 Format Example

```text
# dagim v1

node people-think-in-graphs: People think in graphs

node existing-tools-bias-trees: Existing tools bias trees

node graph-reticence-ui-problem: Graph reticence is a UI problem
  parent people-think-in-graphs  # People think in graphs
  parent existing-tools-bias-trees  # Existing tools bias trees

node terminal-dag-editor-experiment: Terminal DAG editor experiment
  parent graph-reticence-ui-problem  # Graph reticence is a UI problem
```

### 7.3 Format Rules

The file format is line-oriented UTF-8 text.

Rules:

1. A file contains exactly one graph.
2. Blank lines are allowed and ignored semantically.
3. Comments begin with `#` and may appear anywhere a blank line may appear.
4. A node block begins with:

   ```text
   node <node-id>: <node text>
   ```

5. A parent reference appears inside a node block as:

   ```text
     parent <parent-node-id>  # <optional parent text hint>
   ```

6. Parent lines must be indented by two spaces in canonical output.
7. Node IDs are parsed as the token after `node` or `parent`.
8. Node text is parsed as the text after `node <node-id>:` with leading and trailing whitespace trimmed.
9. Internal whitespace, case, punctuation, and symbols in node text are preserved.
10. Empty node IDs are invalid.
11. Empty node text is invalid.
12. Newlines inside node text are invalid.
13. Duplicate node IDs are invalid.
14. Duplicate node text is allowed, though the UI may warn when exact duplicates are created.
15. Parent references must resolve to declared node IDs.
16. Parent references may refer to nodes declared later in the file.
17. Parent text hints after `#` are non-authoritative and ignored by the parser.
18. Self-edges are invalid.
19. Duplicate edges are invalid.
20. Cycles are invalid.

Node IDs should be readable ASCII slugs generated from the initial node text:

1. Lowercase where practical.
2. Tokenize words and numbers.
3. Drop low-information words for longer labels.
4. Drop common measurement quantities and units when they are likely to be incidental to identity.
5. Deduplicate repeated tokens.
6. Cap generated IDs to a compact readable length.
7. If no useful slug remains, use `node`.
8. If the slug already exists, append `-2`, `-3`, and so on.

The implementation may refine slugification for Unicode text, but the generated ID must be stable, readable, compact, and unique within the file.

### 7.4 Comments

For version 1, comments are allowed as standalone lines anywhere in the file:

```text
# This is a comment.
```

On parent lines, `#` begins an optional readability hint:

```text
parent graph-reticence-ui-problem  # Graph reticence is a UI problem
```

Canonical output may shorten long parent hints. Hints are for source readability only and do not affect parsing or graph identity.

A `#` inside node text is ordinary text:

```text
node review-rfc-42: Review RFC #42
```

The serializer may preserve comments if practical, but preserving comments is not required for the first implementation. If comment preservation is expensive, the first implementation may load comments and drop them on save, but this behavior should be documented in the UI or help text.

### 7.5 Canonical Serialization

When saving, the tool should write a canonical form:

```text
# dagim v1

node <node-id>: <node text>
  parent <parent-id>  # <parent text hint>
  parent <parent-id>  # <parent text hint>

node <node-id>: <node text>
```

Canonical serialization rules:

1. Emit the header comment `# dagim v1`.
2. Preserve node file order.
3. Emit each node exactly once.
4. Emit parent references under the child node.
5. Sort parent references by file order, not alphabetically.
6. Emit current parent text hints in canonical parent lines.
7. Shorten long parent text hints to keep source and diffs readable.
8. Separate node blocks with one blank line.
9. End the file with a newline.

### 7.6 Why Parent References Only

The file stores parent references only, not child references.

Benefits:

1. Each edge is stored once.
2. Children are computed from parent references.
3. There is no redundant parent/child state to keep synchronized.
4. Adding a parent is a one-line diff.
5. Unlinking a parent is a one-line deletion.
6. Renaming a node is a small, stable diff because edge identity uses IDs.

## 8. Example Diffs

### 8.1 Adding a Node

```diff
+# dagim v1
+
 node people-think-in-graphs: People think in graphs
+
+node existing-tools-bias-trees: Existing tools bias trees
```

### 8.2 Adding a Parent

```diff
 node graph-reticence-ui-problem: Graph reticence is a UI problem
   parent people-think-in-graphs  # People think in graphs
+  parent existing-tools-bias-trees  # Existing tools bias trees
```

### 8.3 Unlinking a Parent

```diff
 node graph-reticence-ui-problem: Graph reticence is a UI problem
   parent people-think-in-graphs  # People think in graphs
-  parent existing-tools-bias-trees  # Existing tools bias trees
```

### 8.4 Renaming a Node

Renaming a node changes its declaration text. References keep using the same ID. Canonical save may also refresh non-authoritative parent text hints.

```diff
-node existing-tools-bias-trees: Existing tools bias trees
+node existing-tools-bias-trees: Existing tools encourage tree thinking
 
 node graph-reticence-ui-problem: Graph reticence is a UI problem
   parent people-think-in-graphs  # People think in graphs
-  parent existing-tools-bias-trees  # Existing tools bias trees
+  parent existing-tools-bias-trees  # Existing tools encourage tree thinking
```

## 9. CLI Behavior

### 9.1 Primary Invocation

```text
dagim FILE
```

Behavior:

1. If `FILE` exists, load it.
2. If `FILE` does not exist, create a new empty graph associated with that path.
3. Open the interactive TUI.
4. Manual sequencing is entered from inside the TUI, not via a separate CLI command.

### 9.2 Other CLI Options

Useful basic options:

```text
dagim --help
dagim --version
dagim --check FILE       # parse and validate without opening TUI
```

Optional later options:

```text
dagim --print FILE       # print canonicalized file to stdout
dagim --export-dot FILE  # export Graphviz DOT
```

Do not implement optional later options unless the version 1 implementation is already solid.

`dagim --check FILE` should:

1. Parse the file.
2. Validate node IDs, parent references, duplicate edges, and cycles.
3. Print useful graph stats on success, such as node count, edge count, and root count.
4. Report whether the file differs from canonical formatting, without modifying it.
5. Exit nonzero on parse, validation, or canonical-format errors if a strict/check mode is later added; v1 may exit zero for valid but noncanonical files if it clearly reports the formatting status.

Normal TUI save should preserve existing node IDs. Rekeying is an explicit migration/refactor operation because node IDs are stable identity.

## 10. TUI Overview

The TUI should optimize for keyboard-first editing and navigation.

The main experience is not a drawn graph. The main experience is moving through focused textual neighborhoods and graph frontiers.

Primary views:

1. Node view.
2. Search/jump view.
3. Roots view.
4. Manual sequence mode.
5. Help/command view.

The core capture loop should emphasize defining graph relationships while ideas are being created:

1. From the top-level or empty state, add a new node quickly.
2. From a selected node, add or link a parent quickly.
3. From a selected node, add or link a child quickly.
4. When adding a parent or child, select an existing node through search/autocomplete or create a new node from the prompt.
5. Support adding many top-level/root nodes first, but do not make "bulk capture now, link later" the only efficient workflow.

## 11. Node View

The node view is the default focused editing view.

Example:

```text
Parents
────────────────────────────────────────
  People think in graphs
  Existing tools bias trees

Current node
========================================
Graph reticence is a UI problem

Children
────────────────────────────────────────
  Terminal DAG editor experiment

Commands
────────────────────────────────────────
a add node    p add parent    c add child    x unlink
i inspect     r rename        d delete       / search
f roots       m sequence      J/K reorder    w save
R rewrite     q quit          ? help
```

### 11.1 Node View Behavior

The user should be able to:

1. Focus parent nodes.
2. Focus child nodes.
3. Add a new node.
4. Rename the current node.
5. Delete the current node.
6. Add/link an existing or new parent.
7. Add/link an existing or new child.
8. Unlink an existing parent or child.
9. Search all nodes by text.
10. Inspect a node to see details such as its ID.
11. Save.

Normal node, roots, search, and sequence lists should show node text without inline IDs. Long node text should wrap to the terminal width. Node IDs should be available through inspect views, not through the main scanning surfaces.

### 11.2 Suggested Keybindings

These are proposed defaults, not sacred API.

```text
j / Down      move selection down
k / Up        move selection up
Enter         focus selected node
Esc           go back / cancel current prompt
/             search nodes
a             add node
p             add/link parent to current node
c             add/link child to current node
x             unlink selected relationship
i             inspect selected node, or current node if no relationship is selected
r             rename current node
d             delete current node, with confirmation if it has edges
f             show roots view
J / K         move current node later/earlier in file order
m             enter manual sequence mode
w             write/save file
R             rewrite file: regenerate IDs, update references, save canonical format
?             help
q             quit, prompting if unsaved changes exist
```

## 12. Add and Link Behavior

### 12.1 Add Node

When adding a node:

1. Prompt for single-line node text.
2. Trim leading and trailing whitespace.
3. Reject empty text.
4. Generate a readable, unique node ID from the text.
5. Do not require the user to type or approve the ID during ordinary capture.
6. If the exact node text already exists, warn and offer to focus the existing node instead, but allow creating a separate node with a different generated ID.
7. Add the node to the persistent file order.

### 12.2 Add Parent

From current node `B`, adding parent `A` means adding:

```text
A -> B
```

Behavior:

1. Prompt with autocomplete over existing node text.
2. If the selected text matches an existing node, use that node's ID.
3. If the text does not match an existing node, offer to create a new node and generate an ID for it.
4. Reject if the edge already exists.
5. Reject if it would create a cycle.
6. On success, keep focus on the current node unless user preference later says otherwise.

### 12.3 Add Child

From current node `A`, adding child `B` means adding:

```text
A -> B
```

Behavior mirrors Add Parent.

### 12.4 Unlink

Unlinking removes an edge but does not delete either node.

From current node:

1. If a parent is selected, remove `parent -> current`.
2. If a child is selected, remove `current -> child`.
3. Confirm only if the UI makes accidental unlinking likely.

## 13. Rename Behavior

Because node identity is the stable ID, rename changes only the node's text label by default.

Rename:

```text
old text -> new text
```

Rules:

1. Reject empty new text.
2. If the new text already exists on another node, warn before accepting.
3. Update the node declaration text.
4. Preserve the node ID.
5. Preserve all incoming and outgoing edges.
6. Preserve file order position.
7. Canonical save may refresh parent text hints that mention the old text.

## 14. Delete Behavior

Deleting a node removes the node and all incident edges.

Rules:

1. If the node has no parents and no children, delete immediately or with light confirmation.
2. If the node has parents or children, require confirmation.
3. Do not delete neighboring nodes.
4. After deletion, focus a nearby node if possible.
5. If graph becomes empty, show an empty-graph state.

Example:

```text
A -> B -> C
```

Deleting `B` removes `B`, `A -> B`, and `B -> C`.

It does not create `A -> C` automatically.

## 15. Search and Autocomplete

Search is central because node text is the primary human-facing label.

Version 1 search should support:

1. Case-insensitive substring matching.
2. Display matches in file order.
3. Keyboard selection.
4. Enter to focus.

Autocomplete prompts for parent/child linking should reuse the same search behavior.

Optional later improvement:

1. Fuzzy matching.
2. Recent nodes.
3. Ranked matches.
4. Alias support.

Do not add aliases in version 1.

## 16. Roots View

The roots view shows all nodes in the actual graph that currently have no parents.

Example:

```text
Unblocked root nodes
────────────────────────────────────────
  People think in graphs
  Existing tools bias trees
```

This view is useful because it shows the initial frontier of the graph.

Rules:

1. Display roots in file order.
2. Do not automatically linearize the graph.
3. Enter focuses a selected node.
4. Search/filter may be available.
5. This view does not mutate graph state.

This view is distinct from manual sequence mode's dynamic frontier. Roots are a property of the graph. The sequence frontier is a property of temporary sequencing state.

## 17. Manual Sequence Mode

Manual sequence mode is the key graph-processing experience.

It is based on the same idea as Kahn’s algorithm for topological sorting, but instead of choosing tied/unblocked nodes automatically, the tool asks the user to choose each next node.

The tool should not present this as “the” topological sort. It is a user-authored valid sequence through the graph.

### 17.1 Mode Entry

Manual sequence mode is entered from inside the TUI, for example with:

```text
m
```

There should not be a required separate CLI command for version 1.

### 17.2 Conceptual Model

Manual sequencing maintains temporary state:

```text
processed: set of nodes already chosen
output: ordered list of chosen nodes
available: nodes whose parents are all in processed
```

The underlying graph is not mutated.

Version 1 should not persist manual sequence state inside the `.dagim` file. A sequence is temporary exploratory state. Users may export a linearized list, undo, reset, or exit the mode without changing the graph.

At each step:

1. Compute all currently available unprocessed nodes.
2. Present them to the user.
3. User chooses one.
4. Add it to the output list.
5. Mark it temporarily processed.
6. Recompute available nodes.
7. Repeat until all nodes are processed or the user exits.

### 17.3 Display

Default display should emphasize:

1. The sequence produced so far.
2. The currently available nodes.

Example:

```text
Manual sequence
────────────────────────────────────────
1. People think in graphs
2. Existing tools bias trees

Available now
────────────────────────────────────────
  Graph reticence is a UI problem

Commands
────────────────────────────────────────
Space pick    Enter inspect    u undo    r reset    e export    Esc exit
```

The mode does not need to display “still blocked” by default. That can make the interface heavier and more like an analysis dashboard. Users should be able to inspect available nodes and temporarily drill into their parent/child neighborhoods if needed.

Optional later enhancement:

```text
show blocked count
show blocked nodes
show why selected blocked node is unavailable
```

### 17.4 Available Node Ordering

Available nodes are displayed in file order by default.

This display order is non-semantic. It does not mean the graph says one available node comes before another.

### 17.5 Inspecting During Sequence

In manual sequence mode:

```text
Enter
```

on an available node should inspect or focus that node without picking it.

A lightweight inspect view should show:

```text
Node text
Parents
Children
```

Returning from inspect mode should return to the same manual sequence state.

### 17.6 Picking

Picking an available node adds it to the output sequence and temporarily removes it from the remaining graph.

Suggested key:

```text
Space
```

### 17.7 Undo

Manual sequencing is exploratory, so undo should be part of version 1.

Rules:

1. Undo removes the most recently picked node from output.
2. The node becomes unprocessed again.
3. Available nodes are recomputed.
4. Multiple undo operations are allowed.

### 17.8 Reset

Reset clears the temporary sequence state.

The graph itself is not changed.

### 17.9 Completion

When all nodes have been picked, show the completed sequence.

Example:

```text
Sequence complete
────────────────────────────────────────
1. People think in graphs
2. Existing tools bias trees
3. Graph reticence is a UI problem
4. Terminal DAG editor experiment

Commands
────────────────────────────────────────
e export    u undo    r reset    Esc exit
```

### 17.10 Exporting the Sequence

Version 1 should support a simple export of the current sequence.

Possible behavior:

1. Prompt for output path.
2. Default to:

   ```text
   <input-file>.sequence.txt
   ```

3. Write one node per line, in chosen order.

Example output:

```text
People think in graphs
Existing tools bias trees
Graph reticence is a UI problem
Terminal DAG editor experiment
```

The exported sequence is not the graph file and should not mutate the graph.

## 18. Cycle Detection

Any operation that adds an edge must check for cycles.

To add:

```text
A -> B
```

Reject if:

```text
A == B
```

or if there is already a path:

```text
B -> ... -> A
```

Error messages should be explanatory and, if practical, show the cycle path.

Example:

```text
Cannot add edge:
  Terminal DAG editor experiment -> People think in graphs

That would create a cycle:
  People think in graphs
  -> Graph reticence is a UI problem
  -> Terminal DAG editor experiment
  -> People think in graphs
```

Raw files loaded from disk must also be validated for cycles. If a file contains a cycle, the tool should refuse normal editing and show a clear validation error with enough information to repair the file manually.

## 19. Graph Algorithms

### 19.1 Children Computation

Children are computed from parent references.

For each node ID `B` with parent ID `A`:

```text
parents[B].add(A)
children[A].add(B)
```

### 19.2 Roots

A root is any node with zero parents.

```text
roots = nodes where parents[node] is empty
```

Display roots in file order.

### 19.3 Manual Sequence

Manual sequence mode is a user-directed topological traversal.

Pseudocode:

```text
processed = empty set
output = empty list

while len(processed) < len(nodes):
    available = []

    for node in file_order:
        if node not in processed and every parent of node is in processed:
            available.append(node)

    if available is empty:
        error: graph is cyclic or invalid

    chosen = user picks one node from available
    processed.add(chosen)
    output.append(chosen)
```

Because the graph is validated as acyclic before entering this mode, `available` should never be empty unless all nodes are processed.

### 19.4 Path Search

Path search is needed for cycle detection and useful error reporting.

To test whether adding `A -> B` creates a cycle, search for an existing path from `B` to `A`.

If found, the cycle is:

```text
A -> B -> ... -> A
```

## 20. Suggested Internal Architecture

The implementation should keep graph logic independent from TUI logic.

Suggested modules/packages:

```text
graph
  core data structures
  add/delete/rename/link/unlink operations
  validation
  cycle detection
  roots and file-order operations
  manual sequence state

format
  parse .dagim files
  serialize canonical .dagim files
  line-numbered parse errors

ui
  TUI state machine
  views
  keybindings
  prompts
  search/autocomplete

cmd
  CLI entrypoint
```

This separation is important. Most correctness should be testable without a terminal UI.

## 21. Suggested Implementation Stack

A good default implementation stack would be:

```text
Go + Bubble Tea
```

Reasons:

1. Easy single-binary distribution.
2. Fast startup.
3. Good fit for terminal applications.
4. Reasonable state/update/view architecture.
5. Keeps the project practical rather than turning it into a language experiment.

This is a suggestion, not a product requirement. The spec is intentionally language-agnostic except where it describes CLI and file behavior.

## 22. State and Persistence

### 22.1 Dirty State

The TUI should track whether the graph has unsaved changes.

Unsaved changes include:

1. Node added.
2. Node renamed.
3. Node deleted.
4. Edge added.
5. Edge removed.
6. File order changed if such a command is added later.

### 22.2 Save

Save behavior:

1. Validate the graph.
2. Serialize canonical text.
3. Write atomically where practical:
   - write temp file in same directory
   - flush/close
   - rename over original
4. Clear dirty state.

### 22.3 Quit

If quitting with unsaved changes, prompt:

```text
Unsaved changes. Save before quitting? [y]es / [n]o / [c]ancel
```

## 23. Error Handling

The tool should provide clear errors for:

1. Empty node text.
2. Empty node ID.
3. Duplicate node ID.
4. Unknown parent reference in file.
5. Self-edge.
6. Duplicate edge.
7. Cycle creation.
8. Invalid file syntax.
9. Delete confirmation for connected node.
10. Save failure.
11. Export failure.

Errors should be specific and actionable.

Bad:

```text
Invalid graph.
```

Good:

```text
Unknown parent on line 14:
  existing-tools-bias-trees

No node with that ID is declared.
```

## 24. Empty Graph Behavior

When opening a new or empty file, show an empty state:

```text
No nodes yet.

Commands
────────────────────────────────────────
a add first node    ? help    q quit
```

## 25. MVP Acceptance Criteria

A version 1 implementation is acceptable when all of the following work:

### 25.1 File Loading

Given:

```text
# dagim v1

node a: A

node b: B
  parent a  # A
```

`dagim file.dagim` loads the graph with nodes `a`, `b` and edge `a -> b`.

### 25.2 File Saving

Saving writes canonical `.dagim` text with one node block per node and parent ID references under child nodes.

### 25.3 Add Node

The user can add a new single-line node from the TUI.

### 25.4 Generate Stable ID

Adding a node generates a readable unique ID from the node text without asking the user to type the ID.

### 25.5 Duplicate Text Warning

Adding a node with text equal to an existing node warns or redirects to focusing the existing node, while still allowing a separate node if the user confirms.

### 25.6 Add Parent

From node `B`, adding parent `A` creates edge `A -> B`.

### 25.7 Add Child

From node `A`, adding child `B` creates edge `A -> B`.

### 25.8 Unlink

The user can remove `A -> B` without deleting `A` or `B`.

### 25.9 Rename

Renaming node ID `a` from text `A` to text `A2` preserves node ID `a`, preserves all edges, and updates canonical parent text hints on save.

### 25.10 Delete

Deleting a node removes that node and all incident edges, but no neighboring nodes.

### 25.11 Cycle Rejection

Given existing graph:

```text
A -> B -> C
```

attempting to add:

```text
C -> A
```

is rejected with a clear message.

### 25.12 Roots View

The user can view all nodes with no parents.

### 25.13 Search

The user can search node text and focus a selected result.

### 25.14 Reorder File Order

The user can move a node earlier or later in persistent file order without changing graph edges.

### 25.15 Check Command

`dagim --check FILE` validates the file without opening the TUI and prints useful graph stats on success.

### 25.16 Rewrite Command

From inside the TUI, `R` asks for confirmation, regenerates node IDs from current node text, updates parent references, writes current canonical format, and saves the file.

### 25.17 Manual Sequence Mode

Given graph:

```text
A -> C
B -> C
```

manual sequence mode initially shows `A` and `B` as available.

If the user picks `A`, then `B` remains available and `C` remains unavailable.

If the user then picks `B`, `C` becomes available.

### 25.18 Manual Sequence Undo

The user can undo the most recent pick and the available set is recomputed correctly.

### 25.19 Manual Sequence Export

The user can export the current or completed manual sequence as one node per line.

## 28. Open Decisions

These can be decided during implementation:

1. Should comments be preserved exactly on save, or can v1 canonicalization drop them?
2. Should the UI primarily say “parents/children” or “blockers/unblocked by”?
3. Should manual sequence export be available before the sequence is complete?
4. Should deleting a connected node require typing the node text, or is a simple confirmation enough?
5. Should search be substring-only in v1, or fuzzy from the beginning?
6. How aggressively should slug generation normalize Unicode text?

Recommended v1 defaults:

1. Comment preservation is nice but not required.
2. Use “parents/children” in node-editing views.
3. Use “available/unblocked” in manual sequence mode.
4. Allow export of partial and complete sequences.
5. Start with substring search.
6. Implement simple readable ASCII slug generation and uniquification.

## 29. Implementation Prompt for Codex

Build `dagim`, a terminal-first editor for small single-file DAGs, using this document as the source of truth.

Start with correctness before UI polish:

1. Implement the graph model and pure operations.
2. Implement parser and serializer for `.dagim` files.
3. Add unit tests for parser, serializer, graph operations, validation, reordering, slug generation, and manual sequence state.
4. Implement CLI entrypoints `dagim FILE` and `dagim --check FILE`.
5. Implement the TUI with node view, search, roots view, file-order reordering, whole-file rewrite/rekey, and manual sequence mode.
6. Ensure cycle rejection and rename behavior are correct.
7. Ensure saving writes stable canonical diffs with visible node IDs and refreshed parent text hints.

The most important product behavior is that the tool never silently collapses the DAG into an arbitrary total order. In manual sequence mode, the user chooses among currently unblocked nodes.
